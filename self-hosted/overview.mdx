Self-hosting Chatwoot gives you complete control over your customer engagement platform — your conversation data stays on your infrastructure, you choose where it lives, and you can customize the experience to fit your exact business requirements. Whether you're driven by data sovereignty, internal compliance policies, or simply wanting to avoid per-seat SaaS costs at scale, deploying Chatwoot yourself is a well-supported path.

## Why Self-Host?

## Before You Start

Review the minimum requirements below before choosing a deployment method. Undersizing your server is the most common reason for a sluggish installation.

### Hardware Requirements

| Workload | CPU | RAM | Notes |
|---|---|---|---|
| Up to 10,000 conversations/day | 4 cores | 4 GB | Minimum supported configuration |
| Up to 20,000 conversations/day | 8 cores | 8 GB | Recommended for active teams |
| Higher volumes | Scale horizontally | 8 GB+ per node | Add more application servers |

<Note>
  Add at least **1 GB of swap** to every server. Chatwoot runs database migrations during upgrades that can briefly spike memory usage.
</Note>

### Software Requirements

- **Operating System:** Ubuntu 20.04 LTS is officially supported. Most Unix-based systems work, but are not officially supported. Windows is not supported — use a Linux VM.
- **PostgreSQL:** Latest stable version recommended (the only supported database).
- **Redis:** Version 7.0 or higher.
- **Ruby:** 3.2 or later (only required for manual/Linux installs).
- **Node.js:** 20.x or later (only required for manual/Linux installs).

### Storage Planning

Chatwoot stores file attachments (images, documents, audio) sent through conversations. The volume depends heavily on your inbox types and conversation frequency. For anything beyond a small team, use a cloud object storage provider (Amazon S3, Google GCS, Azure Blob, or an S3-compatible service like DigitalOcean Spaces or MinIO) rather than local disk. This keeps your attachments safe across deployments and upgrades.

## Platform Architecture

A production Chatwoot installation consists of the following services working together:

- **Web server** — serves the Rails application and the Vue.js frontend
- **Worker** — runs Sidekiq background jobs (email sending, webhook delivery, notification processing)
- **PostgreSQL** — primary relational database for all application data
- **Redis** — job queue, caching, and real-time pub/sub
- **Object storage** — stores file attachments (local disk, S3, GCS, Azure, or S3-compatible)
- **SMTP / email service** — transactional email for agent notifications, password resets, and email channels

For smaller deployments, the web server and worker can run on the same machine. For higher traffic, run them on separate servers and point both at the same database and Redis instance.

## Telemetry

Chatwoot self-hosted installations send anonymized usage statistics to Chatwoot's servers once per day. This data includes aggregated counts of users, accounts, and inbox types — **never your conversation content or customer data.** The Chatwoot team uses this information to understand feature adoption and prioritize development.

To opt out, set the following environment variable in your `.env` file:

```bash
DISABLE_TELEMETRY=true
```

<Info>
  Telemetry data is stored on Chatwoot-owned infrastructure and processed according to the [Chatwoot Privacy Policy](https://www.chatwoot.com/privacy-policy/).
</Info>
